# CodeCup.tech

Платформа онлайн-контестов для разработчиков.

- **Backend** — Django 5.2 + Django REST Framework + PostgreSQL (корень репозитория)
- **Frontend** — Next.js 15 + TypeScript + Tailwind + shadcn/ui (`/frontend`)
- **Auth** — только через Telegram-бота
- **Язык интерфейса** — русский

План разработки: [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md)

---

## Локальный запуск

Нужны Python 3.12+, Docker и Node 20+.

```bash
cp .env.example .env          # затем впишите DJANGO_SECRET_KEY
make install                  # виртуальное окружение и зависимости
make up                       # Postgres в Docker
make migrate
make run                      # http://127.0.0.1:8000
```

Проверка: `curl http://127.0.0.1:8000/api/health/` → `{"status":"ok","database":"ok"}`

| Адрес | Назначение |
|---|---|
| `/api/health/` | состояние сервиса и базы |
| `/api/docs/` | Swagger UI |
| `/api/schema/` | схема OpenAPI |
| `/admin/` | админка Django |

### Администраторы

Права администратора — это `is_staff`. Есть два пути:

**Уже входили через Telegram** — просто выдать права:

```bash
make make-admin WHO=@AmiriCode
```

**Аккаунта ещё нет** — создать вручную. Команда спросит Telegram ID
(числовой, не @username — узнать его можно у бота @userinfobot):

```bash
make superuser
```

Пароль нужен только для админки Django на `/admin/`. Собственная админ-панель
на сайте работает по входу через Telegram.

> Указывайте **свой настоящий** Telegram ID. Если поставить произвольный, то
> при первом входе через бота создастся второй, отдельный аккаунт — без прав.

Команды: `make help`. Тесты — `make test`, стиль — `make lint` и `make format`,
пересоздать базу с нуля — `make reset-db`.

## Вход через Telegram

Аутентификация устроена так: сайт выдаёт одноразовый код, пользователь
подтверждает вход в боте, сайт обменивает код на сессию в httpOnly-куках.

```
Браузер                     Backend                      Telegram
  │ POST /api/auth/telegram/start/ │
  │◀── nonce + client_secret ──────│
  │ открывает t.me/<бот>?start=<nonce> ────────────────────▶│
  │                                │◀── вебхук /start <nonce>│
  │                                │─ «Подтвердить вход?» ──▶│
  │ опрос status/ раз в 2 сек      │                         │
  │                                │◀── нажата кнопка ───────│
  │◀── {"status":"confirmed"} ─────│
  │ POST exchange/ {nonce, client_secret}                    │
  │◀── Set-Cookie: cc_access, cc_refresh ──                  │
```

`nonce` проходит через Telegram открытым текстом, поэтому сам по себе он
сессию не даёт: обменять его можно только вместе с `client_secret`, который
остался в браузере. Код одноразовый и живёт 5 минут — по истечении срока
экран входа показывает «Ссылка устарела».

### Запуск бота

Бот умеет работать двумя способами. Обработчик апдейтов у них общий, так что
поведение одинаковое.

**Длинный опрос — для разработки.** Ничего, кроме токена, не нужно:

```bash
make bot
```

Без Makefile — то же самое: `.venv/bin/python manage.py codebot`

Команда снимает вебхук (Telegram не отдаёт `getUpdates`, пока он висит),
подключается к API и ждёт сообщений. Остановка — Ctrl+C. Флаги:
`--timeout` — сколько секунд держать соединение, `--keep-webhook` — не
снимать вебхук.

**Вебхук — для продакшна**, см. ниже.

### Настройка бота локально

1. Получите токен у [@BotFather](https://t.me/BotFather) и впишите в `.env`
   `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME`.
2. Придумайте `TELEGRAM_WEBHOOK_SECRET` — любая случайная строка.
3. Поднимите туннель, чтобы Telegram достучался до localhost:

   ```bash
   cloudflared tunnel --url http://localhost:8000
   ```

4. Зарегистрируйте вебхук на выданный адрес:

   ```bash
   .venv/bin/python manage.py set_webhook https://ваш-туннель.trycloudflare.com
   ```

### Запуск бота

Два способа получать апдейты — оба используют один и тот же обработчик,
поэтому ведут себя одинаково.

**Длинный опрос** (удобно локально, туннель не нужен):

```bash
make bot
```

Без Makefile — то же самое: `.venv/bin/python manage.py codebot`

Команда сама снимает вебхук перед стартом: Telegram не отдаёт апдейты
опросом, пока вебхук установлен, — отвечает 409. Чтобы оставить вебхук на
месте, добавьте `--keep-webhook`. Остановка — Ctrl+C или SIGTERM.

**Вебхук** (продакшн, и локально через туннель):

```bash
python3 manage.py set_webhook https://ваш-туннель.trycloudflare.com
python3 manage.py delete_webhook
```

Тесты бота не ходят в сеть и проходят без токена.

### Эндпоинты авторизации

| Метод | Адрес | Назначение |
|---|---|---|
| POST | `/api/auth/telegram/start/` | выдать код и ссылку на бота |
| GET | `/api/auth/telegram/status/?nonce=` | статус подтверждения (опрос) |
| POST | `/api/auth/telegram/exchange/` | обменять код на сессию |
| POST | `/api/auth/refresh/` | обновить сессию |
| POST | `/api/auth/logout/` | выйти |
| GET | `/api/auth/me/` | текущий пользователь |

## Контесты

`status` — это решение администратора (`draft` / `published` / `archived`), а
`state`, который видит пользователь, вычисляется на чтение из статуса и
дедлайна: `draft`, `live`, `ended`, `archived`. Поэтому контест не может
остаться «идущим» после дедлайна и для перевода в завершённые не нужен ни
cron, ни очередь.

Названия на русском транслитерируются в латинский слаг:
«Создайте инструмент на базе ИИ» → `sozdayte-instrument-na-baze-ii`.
При переименовании контеста слаг не меняется, чтобы не ломать ссылки.

| Метод | Адрес | Доступ | Назначение |
|---|---|---|---|
| GET | `/api/contests/` | все | список, фильтр `?state=live\|ended` |
| GET | `/api/contests/featured/` | все | контест для главной |
| GET | `/api/contests/<slug>/` | все | страница контеста |
| POST/DELETE | `/api/me/notify/` | участник | «Уведомить меня» |
| GET/POST | `/api/admin/contests/` | админ | список и создание |
| GET/PATCH/DELETE | `/api/admin/contests/<id>/` | админ | правка и удаление |
| POST | `/api/admin/contests/<id>/publish/` | админ | публикация |

`featured` всегда отвечает объектом `{"contest": ...}`, где `contest` равен
`null`, если активного контеста нет — это состояние «Сейчас нет активного
контеста» на главной.

Демо-данные из макетов: `.venv/bin/python manage.py seed_demo`.

## Заявки

На контест приходится **одна заявка от участника**: на экране отправки прямо
сказано, что засчитывается последняя версия до дедлайна, — поэтому в базе
одна редактируемая запись, а не история отправок.

Статусы: `draft` → `submitted` → `reviewed`, плюс отдельный флаг победителя.
Наружу отдаётся `display_status`, где победа перекрывает «проверено», — это
и есть четыре бейджа из макетов.

`score` и `reviewer_notes` **никогда не попадают участнику** — ни в своей
заявке, ни в профиле, ни в публичном профиле. Заметки на макете проверки
помечены как внутренние, и эта граница закреплена тестами.

Правила проверяются на сервере, а не только в форме:

- после дедлайна нельзя ни отправить, ни отредактировать заявку;
- в черновик и архив контеста отправить нельзя;
- черновик можно сохранить наполовину, а уже отправленную заявку нельзя
  оставить без ссылок;
- `github_url` обязан вести на репозиторий `github.com`;
- описание — не длиннее 500 символов;
- перейти в `submitted` можно только через `submit/`.

| Метод | Адрес | Доступ | Назначение |
|---|---|---|---|
| GET/PUT | `/api/contests/<slug>/submission/` | участник | своя заявка, черновик |
| POST | `/api/contests/<slug>/submission/submit/` | участник | отправить решение |
| GET | `/api/me/submissions/` | участник | свои заявки |
| GET | `/api/users/<username>/` | все | публичный профиль |
| GET | `/api/admin/submissions/` | админ | очередь проверки |
| GET/PATCH | `/api/admin/submissions/<id>/` | админ | проверка заявки |

Ответ экрана проверки содержит `navigation` с полями `position`, `total`,
`previous_id` и `next_id` — это стрелки и счётчик «3 / 36» на макете.

## Контракт API и типы фронтенда

Схема OpenAPI собирается из кода и служит единственным источником правды
для типов фронтенда:

```bash
make schema
```

Команда пишет `frontend/src/lib/api/openapi.json` и генерирует из него
`frontend/src/lib/api/schema.ts`. Оба файла коммитятся — так изменения API
видно в диффе ревью. Правится только схема, не сгенерированные файлы;
удобные псевдонимы лежат рядом, в `types.ts`.

Генерация идёт с `--fail-on-warn`: любое предупреждение схемы валит сборку,
иначе в типах молча появлялись бы `any` и `string` вместо перечислений.

`state` контеста и `display_status` заявки объявлены перечислениями, поэтому
на фронтенде это union-типы (`"live" | "ended" | …`), а не произвольные
строки. Схема также фиксирует границу конфиденциальности: в типе
`MySubmission` полей `score` и `reviewer_notes` попросту нет.

### Админ-панель

| Метод | Адрес | Назначение |
|---|---|---|
| GET | `/api/admin/stats/` | четыре плитки: пользователи, активные контесты, заявки, ожидают проверки |
| GET | `/api/admin/users/` | список пользователей, `?search=` и `?is_staff=true` |

Интерактивная документация — `/api/docs/`.

## Фронтенд

Next.js 15 (App Router) + TypeScript + Tailwind 4 + shadcn/ui в каталоге
`frontend/`. Интерфейс одноязычный: все тексты лежат в `src/messages/ru.ts`
и взяты из словарей `ru` в макетах без изменений.

```bash
make front-install
make front            # http://localhost:3000
```

Backend должен быть запущен на :8000 (`make run`).

### Оформление

Токены из макетов объявлены в `src/app/globals.css`: фон `#09090b`, зелёный
акцент `#22c55e`, синий `#3b82f6`, шрифты Manrope и JetBrains Mono. Классы
Tailwind называются по смыслу — `bg-ink`, `bg-surface`, `border-line-2`,
`text-muted`.

Компоненты shadcn/ui в `src/components/ui/` **перекрашены на эти токены**:
стандартные `bg-primary` и подобные в тёмной палитре макетов не читаются.
Структура каталога и утилита `cn` сохранены, поэтому `npx shadcn add …`
по-прежнему работает — добавленный компонент нужно будет причесать под
токены, как это уже сделано для кнопки и полей ввода.

### Работа с API

Сессия живёт в httpOnly-куке, поэтому запросы идут по-разному:

- **серверные компоненты** — `src/lib/api/server.ts`, куки перекладываются
  из входящего запроса через `next/headers`;
- **браузер** — `src/lib/api/client.ts` с `credentials: "include"`.

Типы берутся из сгенерированной схемы (`make schema`), псевдонимы — в
`src/lib/api/types.ts`.

> **Важно:** фронтенд и backend должны быть на одном хосте, иначе кука
> `SameSite=Lax` не уйдёт. Локально это `localhost:3000` и `localhost:8000`
> (не смешивайте с `127.0.0.1`), в проде — общий домен вида `codecup.tech`
> и `api.codecup.tech` с `AUTH_COOKIE_DOMAIN=.codecup.tech`.

## Платные контесты

У контеста есть валюта (USD, TJS, RUB) и взнос за участие. Ноль означает
бесплатное участие — отдельного флага нет, чтобы не возникало состояния
«платный, но взнос нулевой».

В платном контесте решение принимается только после **принятого** взноса.
Присланный, но ещё не проверенный чек доступа не даёт.

### Как это выглядит

1. Участник нажимает «Участвовать» и видит реквизиты и сумму.
2. Чек можно прислать двумя способами: файлом прямо на сайте или
   сообщением в Telegram-бот. Второй нужен потому, что чек чаще всего лежит
   в телефоне, где Telegram уже открыт.
3. При выборе бота заявка помечается «ждём чек». Следующее фото или PDF от
   этого человека в боте считается чеком — случайная картинка в чат чеком не
   станет, если заявки в таком состоянии нет.
4. Чек уходит администратору (`TELEGRAM_ADMIN_USERNAME`) с кнопками
   «Принять» и «Отклонить». Копия файла сохраняется у нас, чтобы чек был
   виден и в админ-панели, а не только в переписке.
5. Решение можно принять и в Telegram, и на странице `/admin/payments`.
   Отказ требует причины — участник должен понимать, что исправить.
6. Участник получает уведомление в Telegram. После отказа можно прислать
   новый чек в ту же заявку.

Сумма фиксируется в момент создания заявки: если админ потом поменяет взнос,
уже отправленные чеки не «подорожают» задним числом.

Реквизиты общие для всех контестов и задаются в `.env` через
`PAYMENT_REQUISITES`.

## Автоматические проверки

Три уровня, от быстрого к полному.

**Локально, вручную:**

```bash
make check     # стиль, тесты, линт и сборка фронтенда
```

**Перед каждым push** — необязательный хук, включается один раз:

```bash
make hooks
```

Он гоняет только backend (пара секунд). Сборку фронтенда намеренно оставили
CI: если хук идёт минуту, его начинают обходить через `--no-verify`.
Отключить — `rm .git/hooks/pre-push`.

**В GitHub Actions** — на каждый push в `main` и на каждый pull request
(`.github/workflows/ci.yml`), три параллельные задачи:

| Задача | Что проверяет |
|---|---|
| Backend | ruff, тесты на настоящем Postgres, отсутствие несозданных миграций, сборка схемы без предупреждений |
| Frontend | eslint, типы, продакшн-сборка |
| Схема | что `openapi.json` и `schema.ts` пересобраны после правок API |

Последняя задача закрывает ошибку, которая уже случалась: сериализатор
меняют, а типы фронтенда остаются старыми. CI пересобирает их и падает,
если в репозитории лежат другие.

Проверка `makemigrations --check` ловит соседний случай — поле в модели
поменяли, а миграцию не создали.

## Автопроверка присланных работ

Каждую присланную заявку можно прогнать через четыре проверки. Ни одна
**ничего не блокирует**: у сканеров секретов бывают ложные срабатывания, и
отклонять по ним живую работу нельзя. Это подсказка проверяющему.

| Проверка | Что смотрит |
|---|---|
| Секреты | ключи AWS, GitHub, Telegram, OpenAI/Anthropic, Google, Slack, Stripe, приватные ключи, строки подключения с паролем, закоммиченный `.env` |
| Репозиторий | существует, открыт, не пуст, есть README |
| Сроки | были ли коммиты за время контеста |
| Демонстрация | отвечает ли живая ссылка и с каким кодом |

Результат виден на экране разбора заявки, там же кнопка «Проверить заново».

```bash
python3 manage.py screen_submissions            # непроверенные
python3 manage.py screen_submissions --recheck  # все заново
python3 manage.py screen_submissions --submission 42
```

В продакшне ставится в cron:

```
*/10 * * * * cd /opt/codecup && docker compose -f docker-compose.prod.yml \
    exec -T backend python manage.py screen_submissions >> /var/log/codecup-screening.log 2>&1
```

### Что снижает ложные срабатывания

- Файлы-образцы (`.env.example`, `*.sample`, `*.template`) не сканируются
  вовсе: они существуют ради формата значений.
- Строки с `os.environ`, `process.env`, `your-key`, `changeme`, `<...>`,
  `${...}` пропускаются.
- `node_modules`, `vendor`, `.git`, сборки и lock-файлы не читаются.
- Минифицированные строки длиннее 1000 символов пропускаются.
- Одинаковых находок — не больше пяти на шаблон.

Найденный ключ **не сохраняется целиком**: в базу попадают первые 8 символов
и длина. Хранить чужой секрет у себя — значит перенести утечку к себе.

Задайте `GITHUB_TOKEN` в `.env`: без него GitHub даёт 60 запросов в час.

> Образцы ключей в тестах собираются из кусков строк, а не пишутся целиком.
> Иначе push-защита самого GitHub блокирует пуш — шаблоны обязаны быть
> похожи на настоящие ключи, а значит, класть их в исходник нельзя.
